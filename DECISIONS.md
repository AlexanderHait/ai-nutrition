# Реестр решений TeddY

Здесь лежат **итоговые правила** по каждой закрытой проблеме: что работает сейчас, где это живёт, что было отброшено и почему, и как проверить, что оно не сломалось.

CLAUDE.md — это летопись: как шло расследование, что оказалось не так. Этот файл — противоположность: только конечное состояние, коротко, чтобы найти за секунды.

## Как этим пользоваться

**Перед правкой.** Меняешь узел, функцию или файл — сначала поищи его здесь (`Ctrl+F` по имени). Если он в реестре, у него есть правило, выстраданное на реальной ошибке, и список того, что возвращать нельзя.

**После правки.** Прогони «Проверку» из карточки. Если она больше не проходит — правка задела чужое решение, и это надо не «доделать», а пересмотреть.

**Если новая правка что-то сломала.** Карточка отвечает на главный вопрос: как оно работало до и почему именно так. Дальше — история версий workflow в n8n или `git log` по файлу.

**Заполняя карточку**, обязательно пиши раздел «Отброшено». Половина регрессий в этом проекте — это возврат решения, которое уже пробовали и отвергли.

## Ф-01 · Штрих-код: кому верить — декодеру или зрению

**Симптом.** Упаковка с читаемым кодом опознавалась как «Неидентифицированный продукт» с догадкой вместо КБЖУ из каталога.

**Где живёт.** `2z8MgeEZ8kt4MeBg`, узел `Trust Barcode Source` (v1.1), между `Parse + validate` и `Apply Caption Brand`.

**Итоговое правило.**
* Декодер прочитал **другой** код — верим декодеру (`decoder_wins`).
* Код с префиксом `2` (внутримагазинный) не используется никогда, от любого источника (`in_store_code`): за ним у каждой сети свой товар.
* Во всех остальных случаях код от зрения используется как есть.
* Отброшенный код остаётся в `barcode_rejected` с причиной.

**Отброшено, не возвращать.** Правило `vision_only_code` — «декодер отработал и кода не нашёл, значит зрению не верим». Молчание декодера не доказывает ошибку: на мелком, смазанном или бликующем коде он честно возвращает пустоту. Оба случая, ради которых правило вводилось, закрыты другими проверками — неверная контрольная цифра отсекается в `Parse + validate`, префикс 2 — правилом `in_store_code`.

**Проверка.** Декодер молчит + верный код от зрения → код используется. Декодер молчит + код с префиксом 2 → отброшен. Декодер дал другой код → побеждает декодер. Кэш зрения (узел не выполнялся) → код от зрения используется.

<a id="ф-02"></a>
## Ф-02 · Быстрый путь по штрих-коду без AI

**Симптом.** Фото одного штрих-кода шло через зрение: 11–32 секунды и около 1 ₽, при том что поиск в базе занимает 32 мс.

**Где живёт.** Edge Function `teddy-barcode-decode` (`supabase/functions/`), плюс шесть узлов `2z8MgeEZ8kt4MeBg` между `Normalize Vision Image` и `VISION single pass`: `DECODE Barcode` → `Barcode worth using?` → `LOOKUP Decoded Barcode` → `Build Barcode Vision Result` → `Barcode resolved?`.

**Итоговое правило.**
* Декодер прогоняется на **каждом** фото — он дёшев, угадывать «это фото кода?» не нужно.
* Короткий путь включается только при трёх условиях сразу: код прочитан, занимает **не меньше 6% кадра**, найден в каталоге. Иначе фото идёт обычным путём.
* `Build Barcode Vision Result` собирает ровно тот же вид данных, что отдаёт зрение, — вся цепочка ниже работает без правок.
* Любой отказ (мелкий кадр, нет в каталоге, функция упала, сеть) — обычный путь. Код при этом не теряется, его подхватывает ветка Open Food Facts.

**Отброшено.** Порог по площади убирать нельзя: пачка, случайно попавшая в кадр рядом с тарелкой, подменит собой весь приём пищи.

**Замер 15.08.2026: на практике порог почти никогда не проходится.** Реальные значения `area_ratio` в выполнениях — **0.018, 0.017, 0.048** при пороге 0.06. То есть штрих-код на бутылке, снятой с расстояния вытянутой руки, занимает 2% кадра, и быстрый путь не включается: фото платит полный проход зрения. Ответ при этом остаётся верным — декодированный код доходит до позиции через `Trust Barcode Source`.

**Порог сознательно оставлен как есть.** Снизить его — значит разменять точность (приоритет 1) на скорость (приоритет 5): пачка в углу кадра начнёт подменять весь приём пищи. Других сигналов «это фото именно про код» до прогона зрения нет. Решение о размене — за владельцем.

**Проверка.** Фото кода из каталога — ответ меньше секунды, ноль AI-вызовов. Фото тарелки — работает как раньше.

<a id="ф-03"></a>
## Ф-03 · Галочка только там, где за числами есть источник

**Симптом.** Чистая догадка модели уходила пользователю с ✅, потому что уверенность была высокой. Именно из-за этого сводки удаляли.

**Где живёт.** `Build batch summary` (v4.2) в фото-пути, `Build /v meal` и `Build day meals` в текстовом.

**Итоговое правило.** Пометка «⚠️ проверь» ставится по **источнику**, а не по уверенности. Доверенные `nutrition_source`: `label`, `verified_catalog`, `official_catalog`, `restaurant_catalog`, `verified_reference`, `personal_override`, `receipt_line_sugar_free`, `barcode`, `client_memory`, `cache`, плюс попадание в каталог, прочитанная этикетка или живая ссылка. Всё остальное — с пометкой. Одинаковые КБЖУ у разных блюд считаются одной догадкой на всех и тоже помечаются.

**Отброшено.** Пороги по `match_confidence` как единственное условие. Модель ставит 0.98 на выдумке; в `/v` порог `< 0.80` при догадке ровно `0.80` вообще не срабатывал.

**Правило одно на все три пути** — фото, `/v`, `/day`. Меняешь в одном месте — проверь два других.

**Проверка.** Догадка AI и визуальная оценка тарелки → ⚠️. Каталог, штрих-код, прочитанная этикетка, личная поправка → ✅.

<a id="ф-04"></a>
## Ф-04 · Неофициальный сайт не подтверждает данные

**Симптом.** КБЖУ брались с фанатских меню-сайтов и с сайта-опечатки официального домена, и показывались как подтверждённые.

**Где живёт.** `Strict web nutrition provenance` (v3.1) → `Validate web nutrition` (v3.2) → `Build batch summary` (v4.2).

**Итоговое правило.**
* Официальный источник — только собственный домен бренда по **белому списку**. Для брендов вне списка работает прежний чёрный список агрегаторов.
* **Нет бренда — нет и официального сайта бренда:** любой веб-источник у позиции без бренда становится `unofficial_web`.
* `unofficial_web` числа сохраняет, но получает `catalog_hit: false`, `learning_eligible: false`, `needs_check: true` — в сводке ⚠️, в каталог не попадает, ничему не учит.

**Отброшено.** Выбрасывать числа неофициального источника совсем: позиция падает на чистую догадку AI, а это хуже, чем примерно верное число с честной пометкой.

**Проверка.** `vkusnoitochka.ru` → официальный. `vkusnotochkamenu.ru`, `menuvkusnoitochka.ru`, `vcusnoitochca.ru` → неофициальные. Позиция без бренда с любого сайта → неофициальная.

<a id="ф-05"></a>
## Ф-05 · Пачка — не порция

**Симптом.** Пачка печенья 240 г ушла как 1008 ккал с галочкой.

**Где живёт.** `Apply Printed Package Weight` (v1.1), между `Parse + validate` и `Grocery purchase?`.

**Итоговое правило.**
* Напечатанный вес — самый твёрдый факт, он важнее оценки объёма и каталожной порции. Берётся из `label_name`, затем `package_text`, затем названия.
* Съеденной порцией он считается только там, где упаковку обычно приканчивают целиком: **напитки до 700 г и любые пачки до 150 г**. Тогда `user_portion_locked`.
* Крупнее — число сохраняется (оно верное для пачки и удобно как центр лестницы весов), но источник `package_printed_multiserving`: не доверенный, не зафиксированный, уверенность 0.7 → «вес на глаз».
* «20 г белка» не считается массой упаковки: после единицы проверяется слово про состав.
* Ложка из банки (сметана, творог, паста, масло, джем, соус) исключена из напитков.

**Проверка.** Ehrmann 250 г напиток → доверенный. Печенье 240 г, творог 200 г, рис 1 кг → «вес на глаз». Вес из подписи пользователя не перебивается никогда.

<a id="ф-06"></a>
## Ф-06 · Продуктовый чек — не приём пищи

**Симптом.** Фото заказа Пятёрочки логировалось как съеденное: 6490 ккал за один «приём пищи».

**Где живёт.** `2z8MgeEZ8kt4MeBg`, ветка `Grocery purchase?` → … → `SEND grocery purchase notice`.

**Итоговое правило.**
* Признак — в данных, а не в брендах: у продуктового заказа позиции это упаковки (`receipt_context=true` и `package_context=true`).
* **Условие строгое:** позиций с `purchase_context` не меньше двух и они составляют строгое большинство. Ресторанный чек, тарелка и смешанный чек не затрагиваются; при любом сомнении — старый путь. Нет `items` → `false`.
* Черновик не создаётся, AI-запросов нет, фото-квота **освобождается**.
* Ответ показывает покупку с весом упаковок и предлагает записать съеденное через `/v`.
* Событие пишется в `bot_events` как `photo_grocery_purchase` — обычный `LOG photo analyzed` стоит дальше и на эту ветку не попадает.

**Отброшено.** Порционная догадка на каждую купленную позицию (решение от 05.08) — это всё ещё выдуманный приём пищи.

<a id="ф-07"></a>
## Ф-07 · Строки чека: разные цены = разные товары

**Симптом.** Две строки «Пирожок» по 79 ₽ и 85 ₽ получили одинаковое название «Пирожок Вишневый», обе с галочкой.

**Где живёт.** `Verify Receipt Line Integrity` (v1.2), между `Merge verified + web nutrition` и `Build batch summary`.

**Итоговое правило.**
* Одна строка чека с разными ценами → разные товары. Какой из них какой — неизвестно, поэтому конкретное название снимается, показывается строка чека как есть, уверенность падает до 0.6, в каталог позиция не идёт.
* Напиток калорийнее 65 на 100 мл помечается «проверь». Молочные коктейли и латте исключены.
* Напиток со словами «без сахара», «безсах», «б/сах», zero, зеро, no sugar, sugar free, лайт, light, diet — энергия принудительно обнуляется, ставится `zero_kcal_allowed`.
* Узел ловит собственные ошибки и при поломке отдаёт вход без изменений.

**Отброшено.** Слияние одинаковых строк в «×2»: `Build batch summary` строит список из позиций, редактор блюда работает по индексам массива — пользователь увидел бы строку с удвоенным весом и рядом исключённую, а повторное включение дало бы двойной учёт. Косметика против риска двойного счёта.

<a id="ф-08"></a>
## Ф-08 · Кэш зрения: узла с картинкой в выполнении нет

**Симптом.** Повторно присланное фото давало «Не удалось обработать фото после двух попыток» вместо готовой сводки.

**Где живёт.** `Restore image for barcode rescue` и всё, что ниже `Parse + validate`.

**Итоговое правило.** К `Parse + validate` ведут **два** пути: живое зрение и кэш (`Photo Vision Cache Hit?` → `Use Cached Vision`). На кэше узла `Normalize Vision Image` в выполнении нет. Всё, что ниже по цепочке к нему обращается, обязано переживать его отсутствие — не бросать ошибку, а идти дальше без картинки.

**Проверка.** Три состояния: узел не выполнялся, выполнился без бинарных данных, выполнился нормально. В первых двух — элемент без картинки и без ошибки.

## Ф-09 · Вес на глаз показывается как вес на глаз

**Симптом.** Еда на тарелке получала прикинутый по фото вес, показанный обычным числом, — и пользователь удалял всю сводку.

**Где живёт.** `Build batch summary` (`food_resolver_version: v4.3-portion-guess-visible`) и редактор блюда, действие `med_setg_<draft>_<idx>_<rev>_<граммы>`.

**Итоговое правило.**
* Доверенные `weight_source`: `user`, `caption*`, `receipt_explicit`, `catalog_portion`, `restaurant_catalog`, `official_menu`, `package_printed`, `exact_sku_package`, `standard_piece`, `personal_memory`, `barcode_package`. Всё остальное — `portion_guess` и надпись «вес на глаз».
* При наличии такой позиции кнопка «✏️ Проверить» превращается в «⚖️ Уточнить вес». Новых кнопок не добавлено, роутер колбэков не тронут.
* В редакторе — ряд из пяти готовых весов вокруг текущего значения (для 300 г: 150 · 225 · 300 · 375 · 450). Средняя кнопка — ровно текущий вес.
* После нажатия: `weight_source: 'user_confirmed'`, `user_portion_locked: true`.
* Шестая часть колбэка необязательна — старые кнопки (`±10`, `±25`, навигация, ручной ввод) работают как раньше.

**Петля замыкается сама:** сохранённый приём попадает в `client_food_memory`, и со второго раза вес подставляется автоматически (см. Б-07).

<a id="ф-10"></a>
## Ф-10 · Альбом: защита от двойного счёта, а не слияние

**Симптом.** Альбом из нескольких фото одного товара давал несколько сводок, каждая просила сохранить.

**Где живёт.** `media_group_id` в `meals_draft`, RPC `cancel_album_duplicate_drafts`.

**Итоговое правило.**
* Каждая сводка из пачки честно предупреждает: «это одно фото из нескольких, если на других тот же продукт — сохрани только одну».
* После сохранения гасятся соседние черновики того же альбома, **только если это те же самые товары**: каждая позиция совпадает по штрих-коду, id каталога или точному названию.

**Отброшено.** Полное слияние альбома в один приём пищи: каждое фото — отдельное параллельное выполнение, слияние на лету создаёт гонку за один черновик. Риск потерять сводку ради косметики.

**Известное ограничение.** Если один товар опознан по-разному на двух фото (с одного виден код, с другого нет), совпадения не будет — работает только текстовое предупреждение.

## Ф-11 · Несъедобное и комбо-строки

**Симптом.** «Выбери соус» и «Влажная салфетка» попадали в сводку; «Доставка» и «Пакет» могли попасть в дневник как еда.

**Где живёт.** `Parse + validate`, фильтры `nonFood` и `bundleLine`.

**Итоговое правило.**
* Сравнение **по словам**, а не по границам слова: строка режется на слова по `[^a-zа-я0-9]+`, дальше `startsWith`. Причина — в JavaScript `\b` и `\w` работают только с латиницей, поэтому `\bсалфетк\w*\b` не совпадало никогда.
* Несъедобное отсеивается **всегда**, а не только у чека: экран заказа в приложении содержит те же строки, но `receipt_context` там не выставлен.
* Комбо-строка удаляется только если рядом **не меньше трёх** обычных позиций. Иначе «Комбо + соус» осталось бы одним соусом: потерять еду хуже, чем показать лишнюю строку.

**Проверка.** «Пакетик чая» и «Соус Кисло-сладкий» остаются едой. «Пакет», «Доставка», «Трубочка», «Столовые приборы» отсеиваются. Комбо без состава не трогается.

<a id="ф-12"></a>
## Ф-12 · Личная поправка КБЖУ пересчитывается на текущий вес

**Симптом.** Пользователь однажды поправил коктейль Hyper на 130 г / 117 ккал. В следующий раз бот показал **130 г и 225 ккал** — вес личный, а калории от прежних 250 г. Сводка отменена.

**Где живёт.** `Apply Personal Overrides` и `Prepare smart nutrition` (v3.1-override-scaled-to-weight).

**Итоговое правило.** `personal_override` хранится **ровно как в `client_food_overrides`**, на свой `personal_override_grams`. Пересчёт на текущий вес позиции делает `Prepare smart nutrition`: `factor = grams / personal_override_grams`. Поэтому любое изменение веса ниже по цепочке учитывается автоматически.

**Отброшено.** Прежняя схема: `Apply Personal Overrides` сразу пересчитывал поправку под вес позиции, а `Prepare smart nutrition` брал числа как есть. Между ними стоят два узла, которые меняют вес — `Apply Portion Memory` и `Apply caption portion intent`, — и оба оставляли поправку прежней. Чинить их по отдельности нельзя: следующий узел, меняющий вес, снова про это забудет.

**Важно про порядок.** `Apply Personal Overrides` стоит **до** личной памяти и подписи, а `Prepare smart nutrition` — после. Значит любое абсолютное число, посчитанное в первом, ко второму устаревает. То же самое верно для `catalog_override` — его пока спасает то, что оба узла его пересчитывают вручную. **Новый узел, меняющий `grams`, обязан пересчитать `catalog_override`.**

**Проверка.** Поправка 130 г / 117 ккал, позиция пришла на 250 г:
* личная память 130 г → 130 г / 117 ккал;
* вес из подписи 200 г → 200 г / 180 ккал;
* веса никто не менял → 250 г / 225 ккал;
* поправки нет, вес 0, поправка без веса в таблице → поведение не изменилось.

## Ф-13 · Комбо на экране заказа разбирается на состав

**Симптом.** Фото экрана заказа Rostic's: бот показал одну позицию с названием
«Чикен Хит Большой Комбо Наггетсы (6 шт.) Выбери соус Влажная салфетка Картофель Фри Большой Выбери соус Апельсиновый сок 0,5 л» на 510 ₽. В другой раз — просто «Чикен Хит Большой Комбо», без состава.

**Хуже того:** после того как в фильтр несъедобного добавили «выбери» и «салфетк» (см. Ф-11), склеенная строка стала отбрасываться целиком — **вся еда с экрана заказа пропадала**, в сводке оставался один соус.

**Где живёт.** `VISION single pass`, блок «ЭКРАН ЗАКАЗА И КОМБО».

**Итоговое правило.**
* Состав комбо возвращается **отдельными позициями**, каждая со своим `dish` и `receipt_raw_line`.
* Цена состава — `null`, вся цена стоит у строки комбо: иначе сумма перестанет сходиться с ИТОГ.
* Строка самого комбо тоже возвращается. Дальше её убирает `bundleLine` в `Parse + validate` — но только если обычных позиций не меньше трёх, поэтому комбо без состава не пропадает.
* Служебные строки («Выбери соус», «Влажная салфетка», «Трубочка», «Столовые приборы») не возвращаются вовсе.

**Отброшено.** Разбирать склеенную строку уже после зрения: в ней нет ни цен, ни границ позиций, и восстановить их можно только догадками.

**Проверка** прогоном на настоящем коде `Parse + validate`:

| Что вернуло зрение | Результат |
| --- | --- |
| склеенная строка комбо + соус | **остаётся один соус** — так было до правки |
| комбо + 3 строки состава + служебные + соус | 4 позиции: наггетсы, картофель, сок, соус; комбо убрано |
| комбо без состава + соус | обе позиции на месте, еда не пропала |
| обычный чек Rostic's без комбо | не изменилось |

**Чего не проверил.** Реакцию модели зрения на новый блок — для этого нужна отправка фото. Правка аддитивная и откатывается через историю версий.

<a id="ф-14"></a>
## Ф-14 · Пустой ответ базы не должен обрывать цепочку

**Симптом.** Второй пользователь прислал фото тарелки с подписью и **не получил ничего**. Ни черновика, ни сводки, ни сообщения об ошибке. При этом выполнение в n8n помечено успешным.

**Причина.** Узел `GET Personal Food Overrides` читает `client_food_overrides`. У человека без единой личной поправки таблица пуста, узел отдаёт **ноль элементов**, и в n8n это останавливает всю ветку после него. Зрение отработало, разбор прошёл, а дальше тишина.

Это **ровно та же поломка**, что была у `LOOKUP Food Catalog` 04.08.2026 — и то же лечение.

**Итоговое правило.** У любого узла, который читает из базы и может вернуть ноль строк, обязан быть включён `alwaysOutputData`. Потребитель обязан пережить пустой элемент `{}` — у `Apply Personal Overrides` это уже так: `filter(x => x && x.normalized_key)` отсеивает пустышку, и позиции идут дальше без поправок.

**Как проверить, что не вернулось.** В выполнении смотреть `lastNodeExecuted`: если это узел из побочной ветки (например `CACHE Vision Result`), а не `SEND`, значит основная цепочка где-то оборвалась. Дальше искать первый узел с `"data":{"main":[[]]}`.

**Кого это било.** Всех, у кого нет личных поправок, то есть **всех новых пользователей**. У владельца поправок семь, поэтому у него фото работало всегда.

**Где ещё проверено — и что решено.** Правило не механическое: включать `alwaysOutputData` можно только там, где потребитель переживёт пустой элемент.

| Узел | Что читает | Решение |
| --- | --- | --- |
| `GET Personal Food Overrides` (фото) | `client_food_overrides` | **включено.** `Apply Personal Overrides` отсеивает пустышку фильтром |
| `Read motivation state` (текст) | `client_settings` | **включено.** `Attach motivation state` уже написан под отсутствие настроек: ставит `motivation_settings_exists: false`, и ниже есть ветка `Create motivation state` |
| `GET PostMeal subscription` | `subscription_lifecycle` | **не требуется.** Нет строки — человек не Premium, и `Allow Premium PostMeal` в любом случае вернёт пустой список. Поведение не изменится |
| `GET 1/2/3`, `GET await_dish`, `GET await_weight`, `GET edit draft start/action` | `meals_draft` | **включать нельзя как есть.** `WEIGHT 1` берёт `items[0].json` без проверки: на пустом элементе выйдет карточка с `chat_id: undefined`, то есть ошибка вместо тишины. Сначала нужна защита в потребителе и честный ответ «карточка устарела» |

<a id="ф-15"></a>
## Ф-15 · Личное исправление: имя и порция

**Симптом.** Один и тот же протеиновый коктейль сфотографирован 11 раз за две недели, 9 сводок удалены. Калорийность одной и той же бутылки: 850, 325, 300, 250, 225, 117. Сохранены ровно те две сводки, где было **130 г / 117 ккал** — то есть человек уже сказал боту правильный ответ, а бот продолжал показывать другое.

**Где живёт.** `Apply Personal Overrides` (v2-subset-match) и `Prepare smart nutrition` (v3.2-override-portion-wins-over-guess) в `2z8MgeEZ8kt4MeBg`.

**Две причины.**
1. **Имя сверялось на точное совпадение.** Зрение называет ту же бутылку то «Hyper High Protein Chocolate Cocktail», то «Hyper High Protein Chocolate». Одно пропавшее слово — и исправление терялось, а на его месте появлялась догадка на 850 ккал.
2. **Порция из исправления не использовалась вовсе.** В `client_food_overrides` записано «130 г = 117 ккал». Бот угадывал 250 г и **масштабировал исправление вверх** до 225 ккал. Формально верно, по сути — не то, что человек исправлял.

**Итоговое правило.**
* **Имя.** Кроме точного совпадения работает совпадение по включению слов: исправление применяется, если все значимые слова одного названия целиком содержатся в другом, **у обоих названий не меньше трёх значимых слов**, и подходит **ровно одно** исправление. Другой вкус той же линейки («Vanilla» вместо «Chocolate») не подходит — появилось новое слово. Чужой бренд («Epica» вместо «Teos») не подходит. Короткий ключ («банан») работает только точным совпадением.
* **Порция.** Если у исправления есть вес и вес позиции — **всё ещё догадка**, берётся вес из исправления и помечается `user_confirmed`.
* **Догадкой считается** `estimate`, `fallback_only`, `lookup_required`, `vision_geometry`, `unknown_visual_estimate`, `category_visual_estimate`, `vision_or_package`, `reference_amount_fallback`, `package_printed_multiserving`, `purchase_portion_guess` и пустое значение. Список именно такой — **чего в нём нет, считается надёжным**, чтобы новый неизвестный источник веса случайно не перебило.
* Вес из подписи, с упаковки, из чека, из каталога, из личной памяти и вес, уже уточнённый кнопкой (`user_portion_locked`), не перебиваются никогда.

**Отброшено.**
* **Перевод названий.** «HYPER High Protein шоколадный коктейль» и «…Chocolate Cocktail» — один товар, но сопоставить их можно только переводом, а ошибка перевода привяжет чужие числа с галочкой. Этот случай остаётся неопознанным намеренно.
* **Совпадение по бренду плюс два общих слова.** Ловит русский вариант, но заодно ловит другой вкус той же линейки — «Hyper High Protein Vanilla» получил бы числа шоколадного.
* **Новое значение `weight_source: 'personal_correction'`.** Пришлось бы добавлять его в три независимых списка доверенных источников (сводка, `Validate draft before commit`, `lib/data.ts`), и забытый список означал бы «вес на глаз» на честном весе. Используется `user_confirmed` — человек действительно подтвердил эту порцию, когда исправлял товар. Признак `portion_from_override` оставлен только для разбора.
* **Порог `limit: 20`** у `GET Personal Food Overrides` поднят до 200: с 21-го исправления часть молча терялась.

**Проверка.** Прогон на настоящих строках `client_food_overrides` пользователя:

| Что | Стало |
| --- | --- |
| «Hyper High Protein Chocolate», вес запасной | **130 г, 117 ккал**, `user_confirmed` |
| То же имя целиком, вес запасной | 130 г, 117 ккал |
| Вес назван в подписи 250 г | 250 г, 225 ккал — не тронуто |
| Вес напечатан на упаковке | не тронуто |
| Вес уже уточнён кнопкой | не тронуто |
| «Hyper High Protein Vanilla» | исправление не применено |
| «Йогурт греческий Epica 2%» при исправлении на Teos | не применено |
| Два подходящих исправления сразу | пропущено |

<a id="ф-16"></a>
## Ф-16 · Товар без имени: пометка и просьба про штрих-код

**Симптом.** Бот показывал «Неидентифицированный продукт», «Неопознанный продукт (в упаковке с составом и пищевой ценностью)», «Продукт на основе растительных масел (упаковка фиолетового цвета)» — и предлагал это сохранить. Все три сводки удалены, отмена стопроцентная. У одной при этом стояла **галочка**: этикетка была прочитана, числа верные, не хватало только имени.

**Где живёт.** `Build batch summary` (v4.4-unnamed-product-visible) в `2z8MgeEZ8kt4MeBg` и триггер `learn_client_food_memory` (миграция `20260815160000_memory_does_not_learn_unnamed_products.sql`).

**Итоговое правило.**
* Название-заглушка распознаётся списком признаков, позиция получает `unnamed_product` и **всегда** идёт с «⚠️ проверь» — даже когда числа взяты с прочитанной этикетки. Запись, которую человек не может опознать, он не может и проверить.
* Под сводкой появляется одна строка: «🔍 Один товар не опознан. Сфотографируй штрих-код на упаковке — найду точно». Это единственный дешёвый способ закрыть вопрос: декодер читает полосы за ~300 мс, в каталоге 5584 магазинных товара.
* **Та же просьба показывается и когда имя известно, но за числами нет источника** (`package_context`, нет штрих-кода, `needs_check`) — текст меняется на «Точных данных по упаковке нет». Замер по 45 дням реальных черновиков: подсказка появляется примерно в **2% сводок**, шумом не станет. Тарелка, чек ресторана, упаковка с прочитанной этикеткой и упаковка, опознанная по коду, подсказки не получают.
* **Тот же список признаков стоит в триггере личной памяти.** Иначе заглушка стала бы привычным блюдом, и со второго раза `Apply Portion Memory` начал бы подставлять её вес. Это четвёртое правило рядом с заголовками приёма пищи, названием без букв и невозможной плотностью ([Б-07](#б-07)).

**Список признаков дублируется в двух местах** — в узле сводки и в триггере. Меняя один, проверь второй. Свести в одно нельзя: узел работает до записи в базу, триггер — после.

**Отброшено.**
* **Считать заглушкой любую нераспознанную упаковку** (нет штрих-кода и нет совпадения в каталоге). Срабатывало бы на любом незнакомом товаре с честным именем — пометка перестала бы что-то значить.
* **Выбрасывать числа.** Этикетка могла быть прочитана верно; выбросить их значит уронить позицию на чистую догадку, что хуже.
* **`\w` в правиле.** В JavaScript он не работает по-русски ([Л-01](#л-01)), поэтому в узле сравнение идёт по `[а-я]` на строке, приведённой к нижнему регистру с заменой `ё` на `е`.

**Проверка.** Прогон сводки на 8 наборах: три заглушки помечены и получили подсказку; настоящий товар с этикетки, позиция из каталога и тарелка-догадка не изменились; «Сыр творожный Violette», «Хлеб на закваске» и «Печенье в упаковке Любятово» под правило не попадают. Триггер проверен вставкой шести записей в транзакции с откатом — запомнились ровно две настоящие.

## Ф-17 · Повторное чтение кода: когда оно бесполезно

**Симптом.** Ветка `VISION barcode rescue` стоит ~0.25 ₽ и 1–5 секунд на фото и запускалась там, где помочь не могла.

**Где живёт.** Условие узла `Barcode rescue needed?` в `2z8MgeEZ8kt4MeBg`.

**Доказательство, а не догадка.** Разбор трёх выполнений:

| Выполнение | Что вернул декодер | Что вернуло зрение |
| --- | --- | --- |
| 1087 (черновик 526) | `2001000000531`, EAN-13, 252 мс — **внутримагазинный код, отброшен** | `null` |
| 1100 (черновик 527) | тот же код | **выдумало `4600100000531`** — те же цифры с приклеенным российским префиксом, контрольная цифра не сошлась |
| 1205 (черновик 535) | `codes_found: 0` — кода на фото нет | `null` |

**Итоговое правило.** Ветка запускается, только если декодер **не нашёл на фото ни одного кода** и по позиции ещё ничего про код не решено (`barcode_trust_reason` пуст).
* Декодер уже прочитал код — единственный код на упаковке нам известен, зрение прочитает ровно его или выдумает похожий. Платить не за что.
* Декодер прочитал и мы код отбросили (префикс 2) — то же самое.
* Декодер молчит — смазанный или наклонённый код всё ещё может быть прочитан по цифрам, ветка работает как раньше.
* Кэш зрения: узла `DECODE Barcode` в выполнении нет, чтение падает — try/catch даёт 0, поведение не меняется ([Ф-08](#ф-08)).

**Отброшено.** **Убрать ветку совсем.** Случай «декодер не смог, а цифры под кодом читаемы» реальный, и доказательств, что он не встречается, нет — одно наблюдение (1205) это не доказательство. Отсутствие подтверждения не есть опровержение ([Л-01](#л-01)).

**Проверка.** Прогон условия на 11 наборах: два случая с отброшенным внутримагазинным кодом перестали платить, остальные девять не изменились — фото без кода, кэш зрения, принятый код, чек, тарелка, каталог, упаковка-референс, продуктовая покупка, пустой список.

## Т-01 · AI-чат: откуда берётся вопрос

**Симптом.** Десять дней на любой вопрос приходило «Сейчас AI-сервис временно недоступен». Телеметрия писала `provider_error`, хотя провайдер ни при чём.

**Итоговое правило.** Текст вопроса и `chat_id` берутся из узла с **одним** выходом:

```
={{ $items('User Log')[0].json.content }}
={{ Number($items('User Log')[0].json.chat_id) }}
```
Причина: `$items('Узел')` всегда читает **нулевой** выход. Чат приходит в пятый выход `Switch`, нулевой — это `/start`, и он пуст. Промпт был пустой строкой, агент падал с «No prompt specified» за 11 мс.

**Отброшено (проверено живыми прогонами, все три версии неверны).** «Модели gpt-5.4 не существует» — существует. «Рассуждающие модели не принимают temperature» — OpenRouter лишние параметры молча игнорирует. «Системный промпт падает на `.item`» — не падает.

**Смежное.** У Premium Coach (`hy8M7OgAlY2gM1E8`) причина была другой — не задана привязка учётной записи у `OpenAI`, `Premium Decision` и инструментов агента.

<a id="т-02"></a>
## Т-02 · Системный промпт чата: длина, условия, цены

**Симптом.** Ответы на 1800 знаков; на «планирую есть вне офиса, без готовки» предлагались курица с рисом; на бюджет — выдуманная цена.

**Где живёт.** `c5iL23EFH7GUnRZ7`, `systemMessage` агента `nutrion 2`.

**Итоговое правило.** Порядок блоков: ДЛИНА → СОСТАВ ПРИЁМА → ЦЕНЫ → УСЛОВИЯ (ЖЁСТКИЙ ФИЛЬТР) → ТОВАРЫ ИЗ КАТАЛОГА → ФОРМАТ → ПАМЯТЬ.
* **Длина:** максимум 700 знаков и 8 строк, без вступлений и списков «чего не брать».
* **Условия из сообщения — жёсткий фильтр,** применяется первым: где и как человек будет есть, и всё, что не влезает, выбрасывается. Условия **важнее** привычных блюд из памяти.
* **Условий не названо — не выдумывать их.**
* **Цен нет:** стоимость не называется никогда, бюджет не обещается.
* **Состав:** максимум один товар из категории; инструмент вызывается отдельно на каждую категорию.
* **Образец в промпте помечен как образец формата,** с прямым «Не повторяй его состав», и подобран так, чтобы демонстрировать работу правила.

**Отброшено.** Образец с готовой курицей и рисом: модель воспроизводила его дословно независимо от вопроса. **Пример в системном промпте задаёт не только формат, но и содержание.**

<a id="т-03"></a>
## Т-03 · Товары только из каталога, арифметика на стороне базы

**Симптом.** Чат называл категории («питьевой йогурт без сахара») вместо товаров с полки, а когда начал называть товары — ошибся в умножении на 100 г (295 ккал вместо 377).

**Где живёт.** RPC `search_shop_products_v1`, таблица `retail_chain_brands`, инструмент агента `find_shop_products`.

**Итоговое правило.**
* Магазин определяется по собственным маркам сети. У ВкусВилла, Самоката, Лавки и Азбуки Вкуса полка почти целиком своя — отдаём только их марки. У Пятёрочки, Магнита, Ленты, Перекрёстка — их марку плюс общероссийские бренды, но **никогда чужую собственную марку**.
* Совпадение **только с началом слова** (`'(^|[^a-zа-я0-9])' || stem`): основа «твор» находилась внутри «быстрорастворимый», и запрос про творог возвращал желатин.
* Сортировка по числу совпавших слов, затем по **длине названия**: короткое — обычный товар с полки, длинное — узкая экзотика. Сортировка по белку выносила наверх желатин и протеиновый порошок.
* **Ноль означает «не важно»:** модель охотнее передаёт `0`, чем пропускает параметр.
* RPC отдаёт готовые `kcal_per_package`, `prot_per_package`, `fat_per_package`, `carb_per_package` — модель их складывает и **не пересчитывает сама**.
* Категория (`food_category_ru`) задаётся главным словом: сначала первые три слова, потом всё название. Снеки проверяются **раньше** хлеба, иначе «Батончик протеиновый» попадает в хлеб.

**Известные пробелы.** У половины позиций нет `package_grams` — для них итог не посчитать. Цен в каталоге нет вообще.

<a id="т-04"></a>
## Т-04 · Бот обязан ответить на любой текст

**Симптом.** Два текстовых сообщения бета-пользователя не оставили следа **ни в одной таблице** и остались без ответа: ни `chat_logs`, ни `bot_events`, ни черновика, ни телеметрии.

**Где живёт.** `c5iL23EFH7GUnRZ7`, узлы `Detect unknown slash command` и `Switch`.

**Причина.** У `Switch` пять правил (`/start`, `/day`, `/день`, `/v`, «не начинается со слэша») и **нет запасного выхода**. Текст, который начинается со слэша, но не разбирается как команда, не подходил ни под одно правило и пропадал молча:

* `/` — именно это вставляет кнопка меню команд в Telegram;
* `/ ` — слэш с пробелом;
* `/@ИмяБота` — слэш и упоминание.

**Итоговое правило.** `Detect unknown slash command` теперь помечает такой текст как неизвестную команду, и человек получает подсказку про `/help`. До `Switch` эти строки больше не доходят.

**Отброшено.** Добавлять запасной выход самому `Switch`: у него пять выходов, и вставка шестого сдвигает индексы — риск задеть работающие ветки ради того, что закрывается одной строкой выше по цепочке.

**Проверка.** `/`, `/ `, `/@Бот` → подсказка вместо тишины. `/v творог 250 г`, `/день`, `/qwerty`, обычный текст → поведение не изменилось.

**Осталось незакрытым, того же вида.** У `Route Update` в ингрессе (`5nDSM6up5UnLHGT8`) три правила — text, photo, callback — и тоже нет запасного выхода. Голосовое, видео, стикер и **фото, отправленное файлом**, дают `kind: 'other'` и пропадают молча. В данных таких апдейтов пока ноль, поэтому это дыра на будущее, а не действующая поломка. Закрывается запасным выходом на короткий ответ «понимаю фото, текст и команды».

<a id="т-05"></a>
## Т-05 · Счётные слова и вес не должны прятать еду от каталога

**Симптом.** Черновик 532 — набранная текстом дневная сводка из 12 позиций, все до одной догадка AI, вся сводка удалена. Каталог знает почти всю эту еду, но поиск не совпадал ни разу, потому что строки начинаются со счёта: «Три банана», «2 яйца», «Три бедра куриных». То же с весом внутри строки: «250 г творога».

**Где живёт.** `Prepare Day Catalog Lookup` (v2-strip-count-words) и `Apply Day Catalog` (v2-count-aware) в `c5iL23EFH7GUnRZ7`.

**Итоговое правило.**
* Кроме исходной строки в каталог уходит **очищенная**: без счётного слова в начале и без веса внутри. Исходная отправляется всегда — очищенная только как дополнение.
* **Счёт запоминается и умножает стандартную порцию.** Это главное: `Parse day summary` количество не разбирает вовсе (`explicit_grams` заполняется только явным весом с единицей), поэтому без умножения «Три банана» дали бы один банан — ошибка втрое.
* Вес, названный человеком, по-прежнему важнее любой стандартной порции и любого счёта.
* **Неопределённые количества не чистятся вовсе**: «немного», «несколько», «чуть», «четверть», «полтора», «столовые ложки», число с единицей («250 г…»), счёт больше 20. Там стандартная порция соврёт, и пусть отвечает AI с честной пометкой.
* Родительный падеж закрыт синонимами, а не поиском: «творога», «риса», «яиц», «огурцов», «бананов» и ещё 37 форм (миграция `20260815180000_catalog_genitive_aliases.sql`).

**Отброшено.**
* **Чистить строку вместо исходной, а не в дополнение к ней.** Тогда потерялись бы совпадения, где число — часть названия товара.
* **Считать «немного» за единицу.** Стандартная порция миндаля 30 г случайно подходит, а порция гречки 200 г — нет. Угадывать нельзя.
* **Синонимы «овсяных хлопьев», «сыра», «хлеба», «масла», «курицы», «рыбы»** — по той же причине, что и в [Б-09](#б-09): разброс между обычными вариантами шире ±15%.

**То же правило в `/v`** (`Parse /v command`, v2.8-piece-count). Там механика уже была — для дробей («половина банана» → `portion_factor` 0.5 и очищенное имя), счёт просто подключён к ней же: имя теряет счётное слово для поиска, `portion_factor` умножает стандартную порцию. Число, которое является частью названия товара, защищено списком: «7 дней хлебцы», «5 злаков», «4 сыра», а также счёт больше 20 и число перед единицей измерения.

**Проверка.** Прогон старой и новой версии обоих узлов на настоящих строках черновика 532:

| Строка | Было | Стало |
| --- | --- | --- |
| Три банана | к AI | **Банан, 360 г, 317 ккал** |
| 2 яйца | к AI | **Яйцо куриное, 110 г, 157 ккал** |
| гречка | Гречка варёная, 200 г | не изменилось |
| 250 г творога, столовые ложки киноа, Четверть авокадо, немного миндаля, Кофе | к AI | не изменилось |

Плюс запрос к базе: 10 форм родительного падежа находятся, «Шефролл остр сл», «Малый Картофель фри», штрих-код и Alpen Gold не изменились, а «овсянка», «сыра», «хлеба», «масла», «творог exponenta вишня», «молоко простоквашино 950» по-прежнему не находятся.

<a id="д-01"></a>
## Д-01 · Телеметрия пишет текст ошибки

**Симптом.** AI-чат молчал 10 дней. В `ai_usage_events` у всех отказов стоял обезличенный `error_code = 'provider_error'`, поэтому казалось, что виноват провайдер. Настоящая причина — «No prompt specified», то есть запрос до провайдера вообще не доходил — была видна только внутри выполнения n8n. Поиск занял два десятка запросов вместо одного взгляда.

**Где живёт.** Колонка `ai_usage_events.error_message` и пять узлов телеметрии: `Build nutrition AI telemetry`, `Build SMART day telemetry`, `Build SMART v telemetry`, `Build motivation AI telemetry` (текст), `Build Photo AI Failure Telemetry` (фото). Пишут `LOG AI Usage Direct` и `LOG Photo AI Failure`.

**Итоговое правило.**
* У каждого узла телеметрии есть общий помощник `emsg(r)`: берёт текст **только из объекта ошибки** — сам объект строкой, `error.message`, `error.error.message`, `error.description`. До 500 символов.
* **Из корня элемента текст не берётся никогда.** У успешного ответа `r.message` — это ответ модели, и он попал бы в поле ошибки.
* Заполняется только при `success = false`.
* У мотивации и у отказа зрения не было даже кода ошибки — теперь есть.

**Отброшено.** Складывать текст в `metadata`: копание в jsonb — ровно та трудность, из-за которой причину и не нашли. Отдельная колонка плюс частичный индекс по отказам.

**Проверка.** Три входа на каждый узел: ошибка строкой («No prompt specified»), ошибка объектом (429 «Rate limit exceeded»), успешный ответ. Первые две дают код и текст, третий — пусто в обоих полях.

**Как этим пользоваться.** Разбор любого отказа теперь начинается с одного запроса:
```sql
select created_at, feature, error_code, error_message
from ai_usage_events where not success order by created_at desc limit 20;
```

<a id="д-02"></a>
## Д-02 · Проверка живости автоматизаций одним запросом

**Зачем.** Молчаливый обрыв цепочки (см. Ф-14) не виден ни в ошибках, ни в списке выполнений: n8n помечает такой запуск успешным. Читать код всех workflow ради поиска таких мест — долго и даёт ложные срабатывания.

**Правило: проверять не код, а выход.** У каждой автоматизации есть таблица, куда она пишет результат. Свежая строка означает, что цепочка дошла до конца. Это надёжнее любого разбора кода.

```sql
select 'утренний план Premium' as автоматизация, max(created_at at time zone 'Europe/Moscow')::text as последняя from premium_daily_plans
union all select 'напоминания Premium',        max(sent_at    at time zone 'Europe/Moscow')::text from premium_nudges
union all select 'дневной дайджест',           max(updated_at at time zone 'Europe/Moscow')::text from digests
union all select 'недельный обзор',            max(created_at at time zone 'Europe/Moscow')::text from premium_weekly_reports
union all select 'обновление Premium-контекста',max(refreshed_at at time zone 'Europe/Moscow')::text from premium_context_snapshots
union all select 'AI Timeline',                max(created_at at time zone 'Europe/Moscow')::text from ai_timeline
union all select 'распознавание фото',          max(created_at at time zone 'Europe/Moscow')::text from recognition_events
union all select 'обучение личной памяти',      max(last_seen_at at time zone 'Europe/Moscow')::text from client_food_memory
order by 2 desc nulls last;
```

**Как читать.** Ежедневные автоматизации должны показывать сегодня или вчера, недельные — не старше восьми дней. Всё, что отстало сильнее, требует разбора.

**Чего эта проверка не показывает.** То, что запускает сам человек: поддержка, `/m`, AI-чат. Там свежесть зависит от того, пользовались ли функцией, а не от исправности. Такие пути проверяются только живой отправкой.

**Результат прогона 15.08.2026:** все плановые автоматизации свежие. `support_messages` молчит с 01.08 — но это не поломка, а отсутствие обращений.

**Симптом.** Добавление колонки `barcode` уронило весь поиск: `each UNION query must have the same number of columns`.

**Добавляя колонку в `food_catalog`, сразу правь этот поимённый список и прогоняй тестовый вызов `v3`.**

## Б-02 · Имя в каталоге хранится с брендом

**Итоговое правило.** `normalized_name` хранится **с приставкой бренда** (`burger king воппер`), `display_name` — без неё. Поиск подставляет бренд в запрос сам через `normalize_food_query_with_brand_v2`.

**Любая новая запись в каталог обязана следовать этому правилу, иначе строка не найдётся никогда.** Именно на этом был сломан `Build Trusted Cache Rows`: он писал имена без бренда, и даже успешная запись была бы ненаходимой.

**Смежное.** Функция поиска читает поле `raw`, не `dish`.

<a id="б-03"></a>
## Б-03 · Магазинный срез Open Food Facts

**Где живёт.** `catalog_scope='barcode_off'`, 5584 позиции со статусом `provisional`; тип совпадения `shop_name` в `lookup_food_catalog_v3`.

**Итоговое правило.**
* Обе функции поиска пускают в поиск по названию только `verified` и `official`, поэтому срез находится по штрих-коду и **не может** дать ложное совпадение по имени.
* Поиск по названию для этой области разрешён отдельным типом `shop_name` с жёсткими условиями: не меньше **трёх** содержательных слов в запросе; **каждое** слово должно найтись в названии (сравнение по основам — отбрасывается до двух последних букв, но не короче четырёх, иначе русская морфология всё ломает); подходить должна **ровно одна** запись.
* Опечатки и частичные совпадения для этой области запрещены.
* Данные краудсорсные и врут (у Pringles было 151 ккал вместо ~530 — порция, помеченная как 100 г), поэтому это `reliable_web` с доверием 85, а не официальный источник.

**Осознанное расхождение.** RPC `cache_barcode_food`, которым бот пишет товар после живого запроса в OFF, ставит `verified`/`branded` — такие записи **участвуют** в поиске по названию. Одна строка на реальное сканирование, риск мал. Если всплывёт ложное совпадение по названию у товара из OFF — причина здесь.

## Б-04 · Смена КБЖУ в каталоге требует подтверждения

**Симптом.** При равном доверии побеждала последняя запись, и один продукт скакал между значениями двух источников.

**Где живёт.** `cache_verified_external_food_catalog`, таблица `food_nutrition_observations`.

**Итоговое правило.** Каждое предложенное КБЖУ фиксируется как наблюдение. В каталог значение попадает, только если выполнено одно из трёх: источник строго надёжнее; значения сходятся с текущими (10% по калориям, 15% по макросам); ровно это значение встретилось **второй раз**. Иначе прежнее значение остаётся, наблюдение копится, RPC возвращает счётчик `held`. Синоним пишется всегда — он про имя, а не про числа.

<a id="б-05"></a>
## Б-05 · Права у новых RPC

**Итоговое правило.** **Создавая RPC, сразу отзывай `EXECUTE` у `public`, `anon`, `authenticated`.** По умолчанию Postgres выдаёт его всем, а публичный ключ сайта открыт по своей природе — через REST API можно было писать в каталог еды снаружи.

Все обращения идут только через `service_role`; это же основание для решения не заводить RLS-политики на таблицах `public`.

<a id="б-06"></a>
## Б-06 · Сутки питания начинаются в 03:00

**Итоговое правило.** Всё, что съедено до 03:00 МСК, относится к предыдущему дню. Правило живёт в **трёх слоях, и сдвигать их можно только вместе** — иначе приём уйдёт во вчера, а «сегодня» останется новым днём, и человек увидит пустой `/today`.

* **База:** `nutrition_day(ts,tz)`, `nutrition_today(tz)`, `nutrition_hour(tz)` (3..26); генерируемая колонка `meals.eaten_day`; семь функций (`bot_client_state_v20`, `coach_scores_v1`, `coach_scores_v2`, `get_current_summary`, `premium_contexts`, `nutrition_context`, `ai_core_refresh_client`).
* **Сайт:** `dayKey()` и `mealDay()` в `lib/data.ts`, константа `NUTRITION_DAY_START_HOUR`.
* **Бот:** `Parse day summary` (текст), `Apply photo meal slot` (фото), `Select meals to delete` (текст).

**Час дня тоже сдвинут:** `expected_share` в `nutrition_context` считается от часа, иначе в час ночи бот решит, что день только начался.

**Явно названная дата не сдвигается** — сдвигается только «сегодня» и «вчера».

**Не тронуто намеренно:** границы месяца в подписках (`subscription_access_v1`) — там своя логика биллинга.

<a id="б-07"></a>
## Б-07 · Личная память учится не на всём

**Симптом.** Заголовок «Обед:» из дневной сводки стал для бота блюдом на 180 ккал, которое человек «ест».

**Где живёт.** Триггер `learn_client_food_memory` на `meals`; чтение — RPC `lookup_client_portion_memory` и ветка `Apply Portion Memory` в фото-пути.

**Итоговое правило.**
* Триггер отклоняет заведомо невозможное: заголовок приёма пищи (`завтрак|обед|ужин|перекус|утро|день|вечер|полдник|ланч` в одиночку), название без единой буквы, плотность выше 9.5 ккал на грамм.
* Привычкой считается блюдо, съеденное **не меньше двух раз**.
* Запрос в память уходит **только** для позиций, у которых вес всё ещё догадка. Вес из подписи, с упаковки, из чека, из каталога и из официального меню не трогается.
* **Вес меняется только вместе с КБЖУ**, пропорционально — иначе калорийность перестанет соответствовать весу.

<a id="б-08"></a>
## Б-08 · HTML-мусор в названиях каталога

**Симптом.** В сводке пользователю показали «Сухарики со вкусом **&quot;**Сливочный лосось**&quot;**». В нормализованных именах мусора было больше: 430 позиций содержали слово `quot` там, где в исходнике стояли кавычки.

**Где живёт.** Триггеры `food_catalog_clean_names_trg` и `food_catalog_aliases_clean_names_trg`, функции `decode_html_entities`, `clean_food_name`, `clean_normalized_food_name`.

**Итоговое правило.** Чистка стоит **на самой таблице**, а не в писателях. В каталог пишут три RPC (`cache_barcode_food`, `import_off_barcode_page`, `cache_verified_external_food_catalog`), завтра появится четвёртый — триггер забыть нельзя, и старые вызовы менять не пришлось.
* `display_name` — раскрываем сущности, схлопываем пробелы.
* `normalized_name` и `alias_normalized` — вдобавок убираем слова `quot|amp|nbsp|apos|laquo|raquo`, в которые сущности превращаются после нормализации. Проверено: «амперметр» и «ампула» не затронуты.
* `&amp;` раскрывается последним, иначе `&amp;quot;` схлопнется в кавычку.
* Если после чистки не осталось ничего — оставляем прежнее значение.

**Отброшено.** Правка в `cache_barcode_food`: она закрывает один путь записи из трёх.

**Две строки оставлены грязными намеренно.** После чистки их имена столкнулись бы с уже существующими: это разные товары одной линейки с разными штрих-кодами («Крупа Пшено шлифованное» Карачихи, «Котлеты по-домашнему» Ложкаревъ). Удалять товар ради косметики нельзя, по штрих-коду они находятся.

**Чего это не дало.** Улучшения поиска я не измерил и не заявляю: прогон до и после на реальной строке показал, что правило `shop_name` работало и с мусором — лишние слова в названии совпадению не мешают. Изменилось то, что мусор больше не показывается пользователю и не может вернуться.

**Проверка.** Регрессия поиска: «Шефролл острый» → `alias`, «Байтсы средние» → `prefix`, «Огурец» → `exact`, штрих-код → `barcode`, Alpen Gold → `shop_name`, «Клубничное» → нет совпадения.

<a id="б-09"></a>
## Б-09 · Каталог находится по обычным словам, а не по справочным

**Симптом.** Из 18 повседневных слов каталог находил 5. «Огурцы», «яйца», «гречка», «рис», «макароны», «картошка», «творог», «кефир», «молоко», «сметана» не находилось ничего — и каждая такая позиция уходила к модели за выдуманным числом. При этом «Огурец», «Гречка, варёная» и «Творог 5%» в каталоге лежали.

**Где живёт.** Данные: `food_catalog_aliases` (63 синонима от 15.08.2026) и статусы семи строк `food_catalog`. Миграция `20260815100000_catalog_everyday_words.sql`.

**Две причины, и обе не в функции поиска.**
1. **Имена записаны справочным порядком слов** — «Гречка, варёная», «Яйцо куриное», «Куриная грудка, готовая». Человек пишет «гречка», «яйца», «грудка». Русские окончания добивают остальное: «огурцы» против «огурец» — две правки, а допуск опечатки одна. «Помидоры» находились случайно, там правка ровно одна.
2. **Базовые молочные лежали `provisional`**, а поиск по названию принимает только `verified` и `official` (карточка [Б-03](#б-03)). Данные были, бот их не видел.

**Итоговое правило.**
* **Чиним данными, а не поиском.** `lookup_food_catalog_v3` не тронута — см. [Б-01](#б-01).
* **Синоним срабатывает на полное совпадение строки.** Поэтому «картошка» ведёт на варёный картофель, а «картошка жареная», «молоко простоквашино» и «творог exponenta вишня» не затрагиваются. Ресторанные запросы с брендом тоже: у них в строке есть приставка бренда.
* **Повышать до `verified` можно только упаковочный продукт с указанной жирностью** — там число задано спецификацией. Каждое проверено дважды: калории сходятся с БЖУ (до 5%) и значение попадает в межквартильный диапазон реальных этикеток из среза `barcode_off`. Повышены семь: Творог 5% и 9%, Кефир 2,5%, Молоко 2,5%, Сметана 15%, Майонез 67%, Йогурт греческий 2%.
* `trust_score` = 85: выше `provisional` (60), но ниже выверенного справочника (92) и официального сайта (100) — настоящая этикетка обязана перебивать типичное значение категории.

**Отброшено.**
* **Правка допуска опечаток в `lookup_food_catalog_v3`** — самая нагруженная функция проекта, ломать её ради окончаний нельзя.
* **Повышение приготовленных блюд** (картофельное пюре, овсяная каша, жареный картофель, борщ). Их калорийность зависит от рецепта, а не от продукта; галочка на такой строке — это догадка, выданная за факт, ровно против [Ф-03](#ф-03). Остались `provisional` и идут к модели с «⚠️ проверь».
* **Синоним «овсянка»** — в каталоге только сухие хлопья (379 ккал), а этим словом называют сваренную кашу (~70). Завысило бы тарелку впятеро: та же ошибка «упаковка вместо порции», что и с пачкой печенья ([Ф-05](#ф-05)).
* **Неоднозначные слова**: «хлеб» (белый или ржаной), «масло» (сливочное или оливковое), «сыр», «курица», «рыба», «паста», «каша», «орехи», «грибы». Проверка на допуск — разброс между обычными вариантами не шире ±15%; «сыр» (220–360) и «майонез» без процента (300–627) её не проходят.
* **Каталог домашних блюд на ~200 позиций** — предлагал сам, данные не подтвердили: реальные промахи это брендовые и ресторанные позиции плюс ошибки переписывания зрением, а не домашняя еда.

**Проверка.** Все 20 находятся, все 4 регрессии не изменились, четыре запроса по-прежнему молчат:
```sql

from lookup_food_catalog_v3($j$[
 {"raw":"огурцы"},{"raw":"яйца"},{"raw":"гречка"},{"raw":"рис"},{"raw":"макароны"},

 {"raw":"Шефролл остр сл","brand":"ROSTIC'S"},{"raw":"Малый Картофель фри","brand":"ROSTIC'S"},
```

## П-01 · Basic при первом `/start` — пробный на 14 дней

**Симптом.** Новый аккаунт получал бессрочный Basic: функция `initialize_telegram_user_v1` вписывала `plan='basic', provider='beta_basic'` без срока. Продавать Basic было нечем.

**Итоговое правило.**
* Basic при первом `/start` выдаётся на 14 дней (константа в функции). Логика доступа сама снимает его по `current_period_end` — без задания по расписанию и без второй копии правил.
* Повторной выдачи нет: вставка с `on conflict do nothing`, добивка трогает только `free/system_default`.
* Лимиты free — 10 фото и 10 AI-запросов, заданы в `subscription_plan_limits_v1`, **не** в `subscription_products` (там продаваемые тарифы, и это закреплено ограничениями).
* За 3 дня до конца и в день окончания уходят предупреждения: RPC `claim_subscription_trial_notices_v1` **в одном запросе отбирает и помечает**, поэтому защита от дублей стоит в самом отборе, а не в коде отправки. Есть сухой прогон `_claim = false`.
* Событие в `bot_events` пишется только после доставки.

## С-01 · Палитра тем задаётся в одном месте

**Симптом.** В светлой теме страница входа разваливалась: тёмный текст на тёмных карточках. На планшете владельца стояла светлая тема, на Mac и iPhone — тёмная.

**Итоговое правило.** Полный набор цветов **обеих** тем задан один раз в `app/globals.css` через переменные, плюс `@media (prefers-color-scheme)` прямо в CSS. Зашитых числами цветов в компонентах нет.

**Отброшено.** Блок `!important` с перечнем конкретных селекторов в `app/layout.tsx`: всё, что в перечень не попало, оставалось тёмным. И задание половины переменных **только** скриптом темы в `<head>` — если скрипт не отработал, страница оставалась без цветов вовсе.

**Проверка.** Скриншоты при 360, 800 и 1280 px в обеих темах, плюс прогон с полностью выключенным JavaScript.

**Смежное по скорости.** `vercel.json` с `"regions": ["arn1"]` — функции должны считаться в одном регионе с базой. И никакого `backdrop-filter: blur()` на прилипших панелях: на Android он считается на каждый кадр прокрутки.

<a id="л-01"></a>
## Л-01 · Общие правила, выученные на ошибках

**Отсутствие подтверждения — не опровержение.** Отбрасывать данные можно при противоречии (декодер прочитал другое) или структурном признаке негодности (префикс 2, неверная контрольная цифра), а не когда вторая проверка просто промолчала. Так родилась регрессия Ф-01.

**`$items('Узел')` читает только нулевой выход.** Для узла с несколькими выходами это молчаливая ловушка — ссылайся на узел с одним выходом (Т-01).

**`\b` и `\w` в JavaScript — только латиница.** Русские слова через них не ловятся никогда (Ф-11).

**Пример в системном промпте задаёт содержание, а не только формат.** Если он не должен копироваться — напиши это явно (Т-02).

**Узлы, собирающие позицию по явному списку полей, теряют новые поля.** Так терялся флаг `provenance_requires_official` в `Validate web nutrition` и мог потеряться `barcode` в `Parse + validate`. Добавил поле выше по цепочке — проверь каждый такой сборщик.

**API n8n не отдаёт credentials ни у одного узла.** Привязку нельзя проверить чтением, только по факту работы. Создавая узел, передавай её явно; если узел молчит — открыть и выбрать учётную запись руками.

**Успешные выполнения у части workflow не сохраняются.** Пустой список executions у ингресса означает «ошибок нет», а не «трафика нет». Реальный объём смотреть в Supabase по `telegram_updates_processed`.

**Длинные повторяющиеся строки не переносить руками.** Потерянные 24 символа base64 дали битый PNG и час ложной диагностики. Сверяй длину.

**После правки узла — скачать код обратно из n8n и сверить с локальным байт в байт**, и прогонять проверки уже на скачанном. `\n` в JSON превращается в настоящий перевод строки: внутри шаблонной строки это безвредно, внутри обычных кавычек — синтаксическая ошибка.

**`update_workflow` атомарен:** одна неудачная операция — не сохранилось ничего. Испорченный черновик откатывается через `restore_workflow_version`.

**Клиентские данные не удалять.** Даже производные (записи `client_food_memory`, выученные из ошибочной сводки) — готовить SQL и отдавать владельцу.
